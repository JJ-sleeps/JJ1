## Reading these numbers

- **The system WebView works as a JS tier.** WebView2 rendered all three pages
  that the static tier returns as empty shells, in 9 of 9 runs, and JJ1's
  distiller turned the result into the same small payload it produces for
  static pages (for example crates.io: 13,571 DOM tokens down to 2,972).
- **It is not lightweight.** A cold WebView2 page costs about 340-395 MB summed
  working set (200-270 MB private) across 8 processes, against 10 MB for the
  static tier. That is 20-40x more.
- **Against headless Chrome the saving is modest.** About 35-40% less summed
  working set (342-395 vs 568-673 MB), but private bytes are roughly equal
  (201-270 vs 229-282 MB). The summed figure double-counts shared pages, so the
  true saving is somewhere between "none" and 40%. The 70-85% target is not met
  on JavaScript pages with this engine.
- **Time** is similar: 3.2-4.1 s for WebView2 (which includes about 1 s of
  waiting for the DOM to stop changing) against 2.2-8.9 s for Chrome.
- **hn.algolia.com**: WebView2 returned more content than Chrome (5,945 vs 1,765
  content tokens). Chrome was run with a fixed 8 s virtual-time budget and the
  probe waits for the DOM to settle, so this is a difference in waiting
  strategy, not in engine capability.

## Not measured

- **Lightpanda.** It has no native Windows build (its README says to install it
  inside WSL), and this machine has neither WSL nor Docker. So the "Lightpanda
  vs WebView" comparison is half done: only the WebView half has numbers.
- **Warm cost.** Every run here is a cold start with a fresh profile. A JJ1
  process that keeps one WebView alive and reuses it for the next page should
  pay most of this memory once, not per page. That is the number that matters
  for an agent session and it has not been measured.
- Three pages, three runs each: enough to see the order of magnitude, not
  enough for fine comparisons.
